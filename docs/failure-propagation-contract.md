# 异常向上层报告的契约

定位：嵌入式流程内核，同一实例串行驱动。节点或完成阶段失败时，本次驱动调用抛异常，由上层决定业务处置。引擎不自动重试、恢复、取消整个实例或回滚，也不新增 FAILED 状态或永久禁用后续低层操作。

## 调用结果

- 从节点 execute、signal、执行监听器和子流程 completing/completed 抛出的未捕获异常，沿同步调用栈到达当前调用方。失败发生在子流程 signal 中时，调用方是该次子流程 signal 的调用者，不会另向之前已经返回的父 start 调用异步报告。
- RuntimeException 原样传播；节点、signal 和执行监听器中的受检异常包装为 PvmException；子流程完成回调中的受检异常包装为 ActivitiException，均保留原始 cause。这两个包装类没有共同的自定义异常父类，集成可在驱动边界统一捕获 RuntimeException 并记录完整 cause。
- 不把失败当作正常返回，不自动继续本次尚未执行的后续操作。performOperation 清理分发标志并丢弃待执行操作；不撤销此前已经启动或准备好的分支。
- 业务行为若自行捕获并吞掉异常，引擎无法推断该业务已经失败。

## 状态不是业务成功标志

isEnded 表示生命周期终态，不表示所有业务、监听器或回调成功。不能在 catch 中根据 isEnded=true 把失败改判为成功：

| 失败位置 | 已发生的状态/副作用 |
| --- | --- |
| 节点、signal、start 监听器 | 异常前写入及副作用保留；后续活动/监听器不自动运行 |
| 正常流程 end 监听器 | 根可能已经 ended=true；异常仍向调用者传播 |
| 子流程 completing | 子流程已经 ended；调用者与子流程关联仍保留，completed 不执行 |
| 子流程 completed | 子流程已经 ended，调用者的子流程关联已清空；父流程是否结束取决于回调抛异常前已做的操作 |
| 取消监听器 | 取消可能只完成了一部分；未完成取消的根不提前提交成功终态，见生命周期事件契约 |

测试中的 completed 在推进父流程之前抛异常，因此父流程仍未结束；不将这个特定结果推广为所有业务回调的保证。

变量 map 写入及对象修改不会自动回滚。测试以变量写入和内存事件列表验证副作用保留，不代表验证了外部 HTTP、数据库或其他业务系统。并行 takeAll 会先准备执行器再逐一启动；某分支异常可能留下已准备但尚未执行业务行为的路径，查询到路径不等于它已成功执行。

## 上层责任与范围

上层在每次 start/signal 等驱动入口捕获异常、记录失败，并决定终止业务、人工介入或其他明确操作；这里不新增“统一从失败位置继续”的 API。原有显式恢复扩展点和恢复测试继续保留，表示调用者在确认状态后可以选择操作，不表示引擎会自行恢复，也不承诺重放副作用只发生一次。

FAILED 状态的存续、失败后是否禁止所有调用、事务回滚、业务补偿和重复投递去重均需独立契约，本轮未引入。结束后 signal 的拒绝及取消成功终态仍遵守 `lifecycle-event-contract.md`。

可执行覆盖：`FailurePropagationContractTest` 的 6 项测试分别使用运行时异常和受检异常，共 12 个场景；覆盖并行分支 execute、signal、start/end 监听器及子流程 completing/completed。既有 `ExecutionRecoveryTest` 和 `TerminalExecutionContractTest` 继续保护原有行为。
